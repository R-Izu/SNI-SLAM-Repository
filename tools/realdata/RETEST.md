# RETEST — 新しい／良い入力が来たときに、まず回す比較

指示書 [[2026-08-18_r4d_fallbackD_decisions]] §3-2(c) に基づく。

## なぜこの文書があるか

2026-08-17〜18 の R4 で決めた構成は、**その時点の入力に合わせた決定を含む**。
とくに **D（ARKit 姿勢を使い、SNI-SLAM にはマッピングだけさせる）** は、
**この撮影条件でトラッキングが収束しなかったから**選んだ結果であって、
手法の優劣として決めたものではない。

**より良い入力が得られたとき、現在の決定を無条件に引き継いではならない。**
新データが来たら、本番に入る前に下記の4項目を回して決定を取り直すこと。

## 決定の前提になった入力条件（2026-08-17 時点の10本）

後から「どの条件下での決定だったか」を復元できるよう、数値で残す。

| 項目 | 範囲 |
|---|---|
| フレーム数 | 1923 〜 8833 |
| 所要 | 64 〜 294 秒 |
| 経路長 | 22.9 〜 176.5 m |

| 床面積（α-shape） | 35.0 〜 288.1 m² |
| 天井高 | 2.576 〜 2.63 m |

**この条件下での実測**：
- SNI-SLAM のトラッキング ATE 中央値 **1.12 m**（`m3_room_a`・6 m 四方の単室）

  （等速度予測を切ると 0.267 → 0.803 m に悪化）
- ハイパーパラメータは**既定値が最良**（反復を増やすと 1.07〜1.31 m に悪化）

## 再試験する4項目

### 1. A vs D — トラッキングが通るか

**最優先。** D を選んだ理由そのものが覆るかを見る。

```bash
conda activate sni-slam
# A（SNI-SLAM がトラッキング）
python -W ignore run.py configs/RealData/<scene>.yaml --output output/RealData/<scene>/run1
python src/tools/eval_ate.py configs/RealData/<scene>.yaml --output output/RealData/<scene>/run1
# D（ARKit 姿勢）
python -W ignore run.py configs/RealData/_D/<scene>.yaml --output output/RealData/_D/<scene>/run1
```

比較するもの：
- **ATE**（A のみ意味を持つ。D は構成上ほぼ 0 になる）
- 平面多様性と**壁方向が直交しているか**（`precheck_scene.py`、ビン幅 5°）
- メッシュのクラス比（A は door 58.9% に崩壊した。D は 14.5%）

**判定**：A の ATE 中央値が **0.3 m 以下**なら A に戻すことを検討する
（この閾値は追補3 §4-3 で main が定めたもの）。

> **A 用の config は消さないこと**（追補4 §3-2(a)）。
> `configs/RealData/*.yaml` が A、`configs/RealData/_D/*.yaml` が D。
> `use_gt_pose` は config の軸として残す。

### 2. 融合方式 — SNI-SLAM vs TSDF

D の構成では SNI-SLAM に残る役割は**深度の融合だけ**である。
同じ姿勢・同じ深度で Open3D の TSDF 統合と比較する。

```bash
python tools/realdata/tsdf_fusion.py --scene-dir data/realdata/<scene> \
    --config configs/RealData/_D/<scene>.yaml --out <出力>.ply
```

比較するもの：意味投影後のクラス比／平面多様性・重力傾き／頂点数／所要時間。

**どちらに転んでも両方の経路を残す**（追補4 §5-3）。

> **2026-08-27 の実測（追補6 §4-2(b)）**：TSDF が明確に優る。`m3_room_a` で
> 深度支持率 0.510 → **0.850**、頂点数 1,713,603 → **152,122**（1/11）。
> さらに SNI-SLAM のメッシャが 30 GB で落ちた `m3_cor_c` / `m3_cor_d`（bound 45 x 3.5 x 27 m）を、
> TSDF は**ピーク RSS 1.6 GB・7 分**で通した。原因は経路の性質の差である：
> SNI-SLAM の Mesher は bound 全体に密グリッドを張る（`m3_cor_c` で 6600 万点）が、
> `ScalableTSDFVolume` は**観測された表面の周りにしかボクセルを確保しない**。
> 廊下のように「広いが中身が空」なシーンでは、この差がそのまま効く。
> **新データでも大きいシーンは TSDF を既定にしてよい。**

### 3. 平面多様性・重力傾き

```bash
python tools/realdata/precheck_scene.py --mesh <mesh> --scene <name> --out <json>
```

**ビン幅は 5°**。1° にすると法線ノイズ（±10° 程度）で山が広がり、
どのビンも閾値 5% に届かず常に 0 方向になる（実際にそのバグを踏んだ）。

### 4. 意味ラベルのクラス比（投影 vs 入力2D）

```bash
python tools/realdata/project_labels_to_mesh.py --mesh <mesh> \
    --scene-dir data/realdata/<scene> --config <config> --out <out>.ply
```

投票済み頂点のクラス比が入力2Dラベルの画素比と**桁で乖離しないこと**。

## ★未解決：新データの再構成品質を自動で測る指標が無い

**新しいデータが来たとき、その再構成が使い物になるかを機械的に判定する手段は、現時点で無い。**
この文書の他の項目と違い、ここは「回せば分かる」ではなく**未解決の課題**である。

これまでに落ちた候補（[[2026-08-26_r4_data_usability_for_journal]] §10、追補6 §1）：

| 候補 | 落ちた理由 |
|---|---|
| 壁法線ヨー角の集中度 | 再構成ノイズと**シーンの幾何的な豊かさ**を混ぜている。L字は構造的に低く出る |
| **深度支持率** | 床面積との順位相関 **−0.929**。分母がメッシュ頂点数なので、bound が広いほど偽の等値面で分母が膨らみ、**広いシーンほど機械的に低く出る** |
| 頂点数/床面積 | 目視評価と符号が逆 |
| completion 中央値 | 符号は合うが n=8 で rho=+0.594（臨界値 0.643 に届かない）。かつ**下位で順序が反転**し、壊れたシーンを見分けられない |

**今の10本には撮影者の目視評価が使えるが、新データには使えない。**（撮影者が毎回同じ基準で
全シーンを見る保証が無く、事前登録の要件を満たさない。ジャーナルでも
「どうやってきれいなシーンを選んだのか」に答えられない。）

**本命は「GT 位置合わせのもとでの、SLAM メッシュ ↔ BIM 表面の距離」**（追補6 §2-3）。
客観的・再現可能で、**位置合わせアルゴリズムと独立**（GT は CloudCompare の手動合わせ）。
BIM が観測の一部しか覆わないので、**距離は BIM が幾何を持つ領域に限って計算する**こと
（未被覆領域を含めると品質ではなく被覆率を測ってしまう）。
**新データにも同じ指標を適用する。** ただしその BIM が必要なので、
**BIM の無い場所を撮った新データには依然として適用できない** —— ここは未解決のまま残る。

## 新しい評価指標を作るときの必須手順

> **既知の良好な結果に当てて値域を確かめてから使う。**
> 文献の一般論（「屋内再構成は 1〜3 cm」等）を対照の代わりにしてはならない。

参照に使う不可侵成果物：`output/Replica/room0_official/260310_test4`

これを怠って一度誤った：`eval_map_vs_depth.py` の accuracy 0.23 m を
「妥当水準 1〜3 cm と桁が2つ違う」として「マップが破綻」と結論しかけたが、
**Replica 参照は 0.430 m とさらに悪かった**（観測点密度 37 万 vs 145 万点に交絡）。
GPU 不要・2 分で確認できた。

## 撮影仕様（次の撮影者へ）

追補2 §3-2 の改訂版に、A-2 の知見を加えたもの。

| # | 仕様 | 根拠 |
|---|---|---|
| 1 | **経路長を短くする** | ループ閉じが実装されていないのでドリフトは戻らない（T-A1） |
| 2 | **計測用に1〜2本だけループを閉じる**（始点の 0.5 m 以内へ戻る） | 「補正のためのループは効かないが、計測のためのループは効く」。GT 無しでドリフトを測れる唯一の手段 |
| 3 | **天井が 2% 以上写るフレームを全体の 25% 以上** | 重力軸推定に floor/ceiling 法線が要る |
| 4 | **なめらかで等速に近い動き。急な回転・停止・加速を避ける** | トラッキングは動きの事前分布に支えられている（等速度予測を切ると ATE が 3 倍悪化） |
| 5 | 廊下および対向室を含む経路 | 繰り返し構造は廊下でしか出ない |
| 6 | 1 シーケンスの長さ | **要再検討**。現データは 64〜294 秒で、長尺が OOM と所要時間の原因になった |
